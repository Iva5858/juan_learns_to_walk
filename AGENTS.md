# AGENTS.md: working on Juan

For AI agents and new Claude Code sessions. Read this first; it saves hours. Human-facing docs: [README](README.md),
[docs/training.md](docs/training.md), [docs/robot.md](docs/robot.md), [docs/runs.md](docs/runs.md).

## What this is

Juan is a real 43 cm, 8-servo biped (Raspberry Pi 4, Hiwonder HTD-35H bus servos, LSM9DS1 IMU). Policies are trained
in MuJoCo with PPO (Stable-Baselines3) on a Mac, exported to numpy, and run on the Pi from a web dashboard.
**The goal is a robot that works in real life.** A simulator number only counts if it predicts the robot.

## How to run things

```bash
uv sync && source .venv/bin/activate          # Python 3.11, exact versions from uv.lock
pytest -q                                     # ~15 s, all must pass (CI: ruff + pytest on every push)
ruff check .                                  # line length 150
python -m robot.dashboard --fake              # the dashboard on stand-in hardware, http://localhost:8000
python scripts/analysis/walk_test.py runs/v7/<a> runs/v7/<b> --verdict     # judge a walker against another
python scripts/analysis/walk_test.py runs/v7/<a> --moves                   # backward, sideways, turning
```

Fine-tunes go through `scripts/finetune.sh` (recipes for every past run: docs/training.md#fine-tune-recipes):
`FROM=runs/v7/<start> STEPS=30000000 ./scripts/finetune.sh v7/juan_v7_NN_name <train.py options>`. It trains, exports
final and best, runs walk_test (with a KEEP / NOT BETTER (no worse) / NOT BETTER (worse) verdict), the moves test and
the shove test, and writes `runs/logs/<name>_report.txt`.

## Conventions that bite if ignored

- **Run names** must be `<generation>/<name>` (v7/, getup/, test/, ...); `train.py` refuses others. Smoke tests go to
  `test/` and are deleted after.
- **New reward terms and settings are off by default** (weight 0, flag 0), so old runs and their configs keep
  behaving as before. Removing a setting: add it to `env_cfg.REMOVED` with its off value, so old configs still load
  and configs that used it fail loudly.
- **One change per experiment.** Stacking several new difficulties at once has stalled runs repeatedly (getup 9-11).
- **Judge by tests, not training reward.** Training numbers mix shoves and random commands; use walk_test, stand_pushes,
  getup_handover. Look at the videos (`runs/<run>/videos/latest.mp4`): every loophole so far (kneeling, headstands,
  bounding, standing on the edge of a foot, a reversed knee, leg jitter) was obvious on video and invisible in totals.
- **Sim-to-real.** Test on the measured servos (`cfg.use_measured_servos()`, the analysis scripts' default) and on
  randomized physics (`--physics-from runs/v7/juan_v7_13_straight`). A policy that only works on the nominal robot
  (e.g. getup_20: 20/20 nominal, 0/20 randomized) is suspect on hardware.
- **Exports are verified.** `export_policy.py` / `export_getup.py` check that the numpy network matches PyTorch and that
  the robot's own `Controller` reproduces the simulator's observations step by step (to ~1e-7). If they fail, don't
  bypass them: the robot would see different inputs than training.
- **Robot code stays numpy-only** and must keep the safety rules (temperature locks, joint-limit clamping, tilt stop,
  link timeouts). Test it on the fake robot (`tests/test_dashboard.py` starts a real server on stand-in hardware).
- **Don't edit a shell script while it runs** (bash reads it as it goes). Write a new one.
- **The Mac is shared with training.** While a run trains, keep your own simulations single-process or few-process;
  use `multiprocessing` with an initializer (macOS spawns fresh workers: module globals aren't inherited).
- **Tests are silent**: `tests/conftest.py` mutes the robot's voice. Keep new tests fast (mark slow ones `@pytest.mark.slow`).

## Where things stand (Nov 2026)

- **Walking:** best walkers `juan_v7_28_takeover_best` (v7_25 + practice taking over from a getup) and
  `juan_v7_29_floors_best` (wider floor friction and slope). On hardware: ~0.2 m/s, survives moderate shoves,
  falls when stopped dead from fast walking (the dashboard eases speed down now). Backward and sideways: no policy
  since v7_20 does them.
- **Getting up:** `biped_rl/tasks/getup.py`. Works in sim from face down on the nominal robot (`juan_getup_20`, and
  `juan_getup_23` = gentler on the servos); not yet on randomized robots, not yet tried on hardware. It ends in a
  ~24 cm lunge; the walker takes over and squares the feet (robot: Drive tab, "Get up"). History of what failed and
  why: the getup docstrings and `docs/experiments-2026-11.md`.
- **Dashboard:** robot/web (tabs Drive, Actions, Status, Setup); old page at `/classic`.
